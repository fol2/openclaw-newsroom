## Decision

```text
R1 FEASIBILITY_GO —
Rust materially reduces retained-observation scan RSS.

FIRST MIGRATION ATOM —
R2 GO — research Rust reconstructs exact useful output
from bounded unit_refs rows. This authorises no product
migration.
```

Python and research-only Rust processed the same 6,450 HTTP-200 rows
(613,281,383 body bytes) from a consistent copied proving snapshot and
emitted the same manifest digest
`sha256:ec31a8baf6bc5a58204ed4551fd58a0fa896bc55b035f5dd90a49c663d97d0cb`.

After launch and IPC, **peak** RSS falls from 661.8 MiB (Python scan
process) to 526.3 MiB (Python parent plus Rust child), a 135.5 MiB /
20.5% reduction. That clears both the 64 MiB and 20% gates. The Rust
child itself peaks at 482.7 MiB.

CPU for the machine gate is Rust child plus e2e parent, not the parent
alone: 1.55 s + 0.065 s = 1.61 s versus Python 1.37 s (about 18%
higher, under the 20% hold). The GO is based on **peak RSS**. Rust e2e
retained 21.0 MiB is dominated by child-process termination and is not
a long-lived Rust worker claim.

R1 does **not** by itself authorise a product migration. One-event
Python resolution still reconstructs 1,233 units and peaks at 864.7 MiB
because it reloads the corpus. The missing-column R2 HOLD is withdrawn.

R2 used the already-retained event `unit_refs` as exact row coordinates
`(proving_run_id, source_id, observation_digest/body_digest)`, not as
computed output. On the same copied snapshot and the same HK-04 event
(1 of 1,233 units), that lookup returned **one** proving row
(86,133 body bytes). Python and research Rust then computed parser /
item / revision / representation / chunk / predecessor identities from
those bodies. The compared fields matched the retained `unit_refs`
oracle, and the useful-output digest was identical:

`sha256:9777c193d16d9abe83307f0e6109145fca777dc66f7002d9d4810974bf5981b0`.

Bounded-path peak RSS falls from 77.7 MiB (Python) to 27.5 MiB (Python
parent plus Rust child), a 50.2 MiB / 64.6% reduction. That clears the
20% gate. Rust child plus e2e parent CPU is 0.00 s + 0.004 s versus
Python 0.61 s. The R2 GO is this same-boundary comparison. It does not
claim that the 864.7 MiB full-corpus peak has been removed from the
product runtime, and it does not authorise implementation.

`FEASIBILITY_GO` / R2 `GO` authorise no implementation.

## Hardware and method

Host: Mac16,10, Apple M4, 10 cores, 16 GiB. Fresh child process per run.
One warm-up and three measured runs except the process-tree snapshot
and supplementary `tracemalloc` cases. R2 was re-measured on the
retained copied snapshot after the unit_refs comparator landed; B10,
E1, D1 and R1 were not re-run. Peak RSS is the maximum of
`/usr/bin/time -l`, `resource.getrusage`, in-process held RSS and, for
the Rust subprocess, combined parent-plus-child `ps` samples. Primary
runs have `tracemalloc` off. The copied store was created with
`sqlite3.Connection.backup` from a read-only source (17,690
observations, 1,686,304,566 body bytes, 1,789,808,640 snapshot bytes,
page size 4,096, WAL). Event identity for one-event cases was prepared
outside the measured child. No daemon was signalled. No queue event was
claimed.

Research Rust: `docs/research/issue-898-ram-cpu-rust`, `rustc` 1.98.0,
`--release`, not a product crate.

## Rust estimate

- R0 idle research binary: 1.7 MiB.
- R1 same-boundary scan: exact row-manifest parity; peak-RSS gate
  cleared after IPC; child-plus-parent CPU under the 20% hold.
- R2 bounded useful output: `GO` on this research comparator. The
  proving table already has `PRIMARY KEY(run_id, source_id, body_digest)`,
  and retained `unit_refs` already carry `proving_run_id` plus
  `observation_digest`. One exact row (86,133 bytes) was enough to
  rebuild the selected event's ingest / revision / representation /
  chunk / predecessor identities. Digest parity and the 20% peak-RSS
  gate both cleared versus the Python bounded path.

R1 proves large-BLOB ownership and hashing is cheaper in a Rust child.
R2 proves a bounded useful-output seam already exists and that a
research Rust child can match it. Neither result authorises product
code, a production crate, or an implementation issue. A later product
atom would still need current-rights evaluation, `assess_content`,
effective-revision resolution, and a decision about whether bodies
return to Python.

Supplementary `tracemalloc` on import costs about 15 MiB and 11 s of
CPU versus the primary import. That contamination is why the withdrawn
packet cannot be used as a Rust decision.
